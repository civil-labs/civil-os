# Changing the schema with Atlas

In civil-os, migrations in `database/migrations` are generated by Atlas from
`database/schema/schema.pg.hcl`. Atlas is licensed for local use only and
runs under the developer's own login. **You never run Atlas.** You change the
HCL, the developer reviews it and generates the migration, and then you review
what was generated.

## Hard rules

These hold even when `atlas whoami` succeeds, Atlas is clearly logged in, the
developer is away, or running the command yourself would be faster.

- **Never run `mise run db:diff`, `mise run db:validate`, or any `atlas`
  command** (`atlas migrate diff`, `migrate hash`, `migrate validate`,
  `migrate apply`, `schema apply`, `schema inspect`, `login`, `whoami`, …).
  That includes running them through another route: a script, a `mise` task,
  `docker run arigaio/atlas`, or a `!`-less shell.
- **Never write or edit anything in `database/migrations/`**, including
  `atlas.sum`. Don't hand-write a migration to unblock yourself, and don't
  "fix" a generated one. If the SQL is wrong, the HCL is wrong.
- **Don't commit a migration you didn't watch the developer generate.** If
  one appears on the branch unannounced, ask where it came from.

## Workflow

### 1. Change the HCL, and only the HCL

Edit `database/schema/schema.pg.hcl` to match the spec or plan. Follow the
conventions already in the file: extensions in `schema.extensions`, the
`legal_valid_range` and `is_voided` patterns, and the existing comment style.
Then run `mise run check`, which doesn't touch Atlas, so the rest of the build
is green.

### 2. Stop, and give the developer the change to review

Before asking for any command, present the change and wait for their answer.
Include:

- **What changed and why**, one line per object (extension, function, table,
  column, index, constraint), with a link to the spec or plan section it
  implements.
- **The diff**, with `git diff -- database/schema/schema.pg.hcl` shown in full,
  or as a pointer to the file and lines if it's long.
- **The SQL you expect Atlas to generate**, statement by statement (`CREATE
  EXTENSION …`, `CREATE FUNCTION …`, `CREATE INDEX …`), so the developer can
  compare it with the real output.
- **Anything you're unsure of in the HCL syntax**, such as an attribute
  no other block in the file uses yet, and the fallback if Atlas rejects it.
- **The operational effects**, such as table locks, long index builds,
  rewrites or data backfills.
- **Whether it needs two passes** (see "Objects that depend on a new
  function" below), and if so, which half goes first.

Ask them to review it and say whether to go ahead. If they ask for changes,
make them in the HCL and present it again. Don't move to step 3 until they
approve.

### 3. Ask the developer to run the commands

Once they approve, give the exact commands, to run with the `!` prefix so the
output lands in the session:

```
! mise run db:diff
! mise run db:validate
```

Tell them that `db:diff` runs `git add --renormalize .` and strips CRs from
every tracked file before it calls Atlas, so it can stage unrelated
line-ending changes. Then wait. If a command fails, read the error, fix the
HCL if that's the cause, and go back to step 2. Never retry the command
yourself.

### 4. Review what Atlas generated

When they've run both commands:

- Read the new `database/migrations/<timestamp>.sql` and the `atlas.sum`
  change.
- Compare it with the SQL you predicted in step 2, statement by statement.
- Check for drift: anything in the migration that your HCL change didn't
  cause. Report it; don't remove it.
- Check what the local tooling needs. `dev/migrate.sh` and
  `testutil.ExecFiles` run each file in a transaction, so `CONCURRENTLY` (or
  `-- atlas:txmode none`) won't work there.
- Run `scripts/check-migrations-size.sh database/migrations`.

Report what you found. If the migration is wrong, change the HCL, ask the
developer to delete the generated file and restore `atlas.sum`, and go back to
step 2. Give the cleanup as two separate commands, so a file that's already
gone doesn't stop `atlas.sum` from being restored (with `&&`, a failed `rm`
skips the `checkout`):

```
! rm -f database/migrations/<timestamp>.sql
! git checkout -- database/migrations/atlas.sum
```

### 5. Test, then commit

With the migration in place, run `mise run test:integration`, which applies
every migration to an empty PostGIS container, and `mise run down && mise run
up`, which applies it through `dev/migrate.sh`. Commit the HCL and the
generated files together, and say in the commit or PR that the developer
generated the migration and ran `db:validate`, with its output.

## Objects that depend on a new function

Atlas doesn't parse SQL strings in the HCL. It can't see that an index `expr`
calls a function, and in a single diff it creates table changes **before** new
functions. So a new function and an index that calls it, generated together,
come out in the wrong order. `db:diff` succeeds, then `db:validate` fails on
replay with `function core.<name>(...) does not exist`. Atlas documents
`depends_on` only for `view` and `materialized` blocks, so the HCL can't fix
the order. A column `default` (`sql("...")`) or a `check` that calls a new
function is probably affected the same way. That hasn't been seen here yet,
so check the order when one comes up.

Use two passes, each one a separate migration:

1. Add the function, plus anything else that doesn't call it, and leave the
   dependent index, default or check out of the HCL. The developer runs
   `db:diff`.
2. Add the dependent object to the HCL. The developer runs `db:diff` again,
   then `db:validate` once over both migrations.

Both migrations go in the same PR. Say in step 2 that the change needs two
passes, so the developer isn't surprised by it. This doesn't apply when the
function already exists in an earlier migration.
`docs/parcel-search/plan.md` (step 1.2) has a worked example: `pg_trgm`,
`core.search_normalize` and the trigram index on `address_attributes`.
